## 2026-07-29 — Greeks are returned in raw units, and scaled only through named functions

The core always returns:

| Greek   | Unit                                               |
| ------- | -------------------------------------------------- |
| `delta` | per 1.0 of spot                                    |
| `gamma` | per 1.0 of spot squared                            |
| `vega`  | per **1.00 of volatility** — 100 volatility points |
| `theta` | per **year**                                       |
| `rho`   | per **1.00 of rate**                               |

Scaling happens exclusively through `greeks/scaling.ts`: `vegaPerPercentagePoint`,
`thetaPerCalendarDay`, `thetaPerTradingDay(theta, tradingDaysPerYear = 252)`,
`rhoPerPercentagePoint`. There is no runtime-configurable scaling and no units option object.

**Why.** A scaled number is indistinguishable from an unscaled one. `theta = -4.31` could be per
year or per day, and with a configurable unit the answer depends on a setting somewhere up the
call stack that the reader of the calling code cannot see. `thetaPerCalendarDay(theta)` cannot be
misread. The cost is one extra call; the benefit is that no returned number is ever ambiguous.

The convention is documented in three places: JSDoc on each function, the README, and
`docs/MATH.md`.

## 2026-07-29 — Normal CDF: Hart/West, not Abramowitz & Stegun 26.2.17

**The reason is absolute accuracy and nothing else.** A&S 26.2.17 carries a stated error bound of
|eps| < 7.5e-8 (measured here: 7.45e-8 at x = 0.718). Hart's rational form in West's
double-precision presentation is near machine precision. For a library whose entire premise is
that its numbers can be trusted, that difference costs nothing to take.

**Do not confuse accuracy with parity.** Put-call parity is a _structural identity_, not a
precision requirement. Algebraically it reduces to

```
C - P = S e^(-qT) [N(d1) + N(-d1)] - K e^(-rT) [N(d2) + N(-d2)]
```

so it holds to machine precision purely because `N(x) + N(-x) = 1`, no matter how accurate `N`
is otherwise. Measured over the documented domain: A&S gives 1.8e-12, Hart/West gives 3.6e-12 —
both far inside the 1e-9 tolerance, and the ordering between them is noise.

The consequence for debugging is the part that matters: **if a parity test fails, the fault is in
the reflection or in the input domain — never in the CDF's accuracy.** The reflection is therefore
implemented explicitly, with `normalCdf(-x)` and `1 - normalCdf(x)` computed from the same
upper-tail routine, so the identity holds by construction and a failure points at the right place.

The Hull benchmark is the opposite requirement: it tests absolute accuracy against published
values, not internal consistency.

## 2026-07-29 — Documented deviation from West's published constants

`normalCdf` uses Hart's rational form below |z| = **3** and a Laplace continued fraction of
**60 levels** above it. West (2005) publishes the branch point at 7.07106781186547 with a 5-level
continued fraction and a 0.65 terminator.

**Measured, against 40-digit ground truth** (`test/fixtures/normal-reference.json`, generated by
exact BigInt fixed-point arithmetic with pi from Machin's formula — no constant is taken on
trust):

| z   | Q(z)     | relative error, West as published | relative error, as shipped |
| --- | -------- | --------------------------------- | -------------------------- |
| 3   | 1.35e-3  | 1.5e-14                           | 0                          |
| 5   | 2.87e-7  | 4.6e-11                           | 1.8e-16                    |
| 7   | 1.28e-12 | 2.6e-9                            | 1.6e-16                    |
| 8   | 6.22e-16 | 8.7e-9                            | 1.6e-16                    |
| 10  | 7.62e-24 | 3.2e-9                            | 1.9e-16                    |
| 20  | 2.75e-89 | 1.7e-11                           | 2.5e-16                    |

Worst relative error anywhere on the line, as shipped: 1.2e-14, occurring just below the branch
point inside Hart's branch. Above the branch point: 2.4e-16.

**Why deviate at all.** West's published constants are tuned for _absolute_ accuracy and they
achieve it — around 1e-16 everywhere, which is what the decision above is about and which is
fully sufficient for pricing, where `N` enters multiplied by `S` or `K`. The published form's
_relative_ accuracy in the tail is the part that degrades, because the value itself has become
tiny.

The practical effect is small and is not claimed to be otherwise: at z = 7 the absolute error of
the published form is about 3e-21. The deviation was taken because the cost is nil, because the
tail branch is genuinely reached by 0DTE and weekly deep-out-of-the-money contracts where d2 sits
around -4.6, and because a deviation that is measured, documented and reproducible is an asset
for a library that sells itself on correctness.

**Constraints this decision carries.**

1. There is no runtime choice between the variants. The library ships exactly one normal CDF.
2. The reference values are permanent test fixtures, generated in exact arithmetic and
   regenerable with `node test/fixtures/generate-reference.mjs`.
3. West's published form is retained as a _comparison baseline_ in
   `test/normal.west-comparison.test.ts` — as a test, not as an option. That test also asserts
   that the published form satisfies its own claim of ~1e-16 absolute accuracy, so the comparison
   is fair rather than a straw man.
4. The deviation is written up here and in `docs/MATH.md`.

## 2026-07-29 — Greeks at the boundary report the limit, and the subgradient midpoint at the kink

When `timeToExpiry` or `volatility` is exactly 0 there is no randomness left, so the payoff is a
deterministic function of the discounted forward and the Greeks are its derivatives:
gamma and vega are 0, and delta, theta and rho follow from `max(S e^(-qT) - K e^(-rT), 0)`.

Two points are conventions rather than derivations, and are stated as such:

- Gamma's true limit at the strike is a Dirac delta, which has no finite value. It is reported
  as 0.
- Exactly at the kink the payoff is not differentiable. Delta is reported as the midpoint of the
  subgradient: 0.5 for a call, -0.5 for a put.

Out of the money every sensitivity is returned as literal `0` rather than `sign * 0`, so a put
never reports `-0` — which compares unequal to `0` under `Object.is` and would surprise anyone
aggregating Greeks across a position.

## 2026-07-29 — Monotonicity properties are asserted against a resolution floor

A Black-Scholes price is a difference of two terms of order `S` and `K`, so it carries an
absolute rounding of a few ulp of the larger. Where the true difference between two prices falls
below that, the computed ordering can invert.

Property tests therefore assert monotonicity with a floor of `8 * eps * max(S, K)`, and assert
_strict_ monotonicity only once the gap exceeds ten times that floor.

This is not a weakened assertion; it was verified rather than assumed. The counterexample that
prompted it — S = 28.8, K = 2.5144595332169533, T = 0.04176592831188112, r = 0, sigma 0.001 vs
1.515616632428247 — was re-evaluated in the cancellation-free form
`C - (S e^(-qT) - K e^(-rT)) = K e^(-rT) N(-d2) - S e^(-qT) N(-d1)`. The true increase is
**5.6e-16**, while one ulp of the price is **5.8e-15** — ten times larger. The price is genuinely
monotone in volatility; the ordering is simply not representable there.

## 2026-07-29 — Reference values are generated, not transcribed

Every expected value for the normal distribution comes from
`test/fixtures/generate-reference.mjs`, which computes in exact BigInt fixed-point arithmetic at
adaptive precision. Two details were found the hard way and are guarded in the generator:

- The working precision must exceed `x^2 / ln 10`, not `x^2 / (2 ln 10)`. Getting it wrong is
  silent: at x = 37 with 600 digits the result was wrong by 3.5e-4 relative while still looking
  like a number. The generator now cross-checks every value at two precisions and refuses to emit
  one where they disagree.
- Values are computed at the exact IEEE-754 double nearest the printed literal, not at the
  decimal literal. `4.6` is really 4.5999999999999996447..., and evaluating Q at the decimal
  instead shifts the result by 1.6e-15 relative — which would have been misread as an inaccuracy
  in the library.

Several values recalled from memory during initial drafting were wrong in the last one or two
digits. That is the reason this generator exists.

## 2026-07-29 — Five defects found by adversarial review, and what they had in common

An adversarial review of `/src` by the `quant-verifier` subagent found five real defects after the
test suite was already green at 146 assertions. All five are fixed and each carries a regression
test. They are recorded here because the pattern is worth remembering.

1. **`crrPrice` returned `Infinity`.** The highest terminal node is `e^(ln S + sigma sqrt(T n))`,
   which overflows for inputs inside the documented domain — `S = K = 100`, `T = 1`, `sigma = 5`,
   `n = 20 000`. A call payoff of `Infinity` propagated to the root. Worse, the failure appeared
   _when the caller raised `n` to get a better answer_: the same contract priced correctly at
   `n = 1000`. Now checked before any work is done, and refused with a message that says what to
   do instead.

2. **`probabilityItmUnderQ` reported an expiring at-the-money put as certain.** The degenerate
   branch returned `terminal > level ? 1 : 0`, and the put case was computed as `1 - above`. At
   `terminal === level` both strict inequalities are false, so both probabilities should be 0 —
   but the complement turned one of them into 1. The library simultaneously priced the put at 0
   and reported a certainty of finishing in the money.

3. **The put probability was `1 - N(d2)` rather than the documented `N(-d2)`.** Algebraically
   identical, numerically not: at `d2 = 10.4` the complement returns a hard 0 where `N(-d2)` is
   1.04e-25 — a representable number the CDF produces to 1.6e-16 relative accuracy. This one is
   the sharpest of the five, because it discarded, in a thin wrapper, exactly the tail accuracy
   that the deviation from West's constants exists to provide.

4. **`normalCdf` truncated the tail at |z| = 37.** The cutoff was justified in a comment by
   `1 - Q(z)` being indistinguishable from 1 beyond it — true, and irrelevant to `Q` itself, which
   stays representable to |z| ~ 38.5. Some nineteen orders of magnitude were being thrown away.
   The cutoff is gone; `Math.exp` underflows on its own where 0 is correct.

5. **`historicalVar` could return `-0`.** Negating a flat return produced `-0`, which compares
   unequal to `0` under `Object.is`. The identical hazard had already been identified and guarded
   in `boundaryGreeks` and was simply not applied here.

**What they had in common.** Four of the five sit at a boundary the tests exercised only from one
side: a strict inequality at the point of equality, a complement in the tail, a cutoff constant, a
signed zero. None was a wrong formula; every formula in the library was correct. The defects were
in the _transitions_ — between the continuous case and the degenerate one, between a representable
value and an unrepresentable one, between an identity that holds in exact arithmetic and its
behaviour in floating point.

A green suite says the cases you thought of pass. It says nothing about the cases you did not, and
the boundaries are where those live.

## 2026-07-29 — Vega at the kink is finite; this supersedes the earlier "gamma and vega are 0"

The entry above on boundary Greeks said gamma and vega are both 0 at the boundary, justifying it
with the Dirac-delta argument. That argument is correct for gamma and **wrong for vega**, and the
entry is superseded on that point.

At the kink — `volatility = 0`, `timeToExpiry > 0` and the forward exactly on the strike —
approaching from `sigma > 0` gives `d1 = sigma sqrt(T) / 2 -> 0`, so

```
vega -> S e^(-qT) sqrt(T) phi(0)
```

which is finite and large: **39.894** for `S = K = 100`, `r = q = 0`, `T = 1`. Reporting 0 put a
jump discontinuity into the library's own output — the analytic branch returns 39.894 at
`sigma = 5e-324` and the boundary branch returned 0 at `sigma = 0`. Gamma is different: it
genuinely diverges, and the code returns 3.99e297 just above the boundary, so 0 remains the only
finite thing to report.

Away from the kink vega really is 0, because the value approaches intrinsic exponentially fast in
`1/sigma^2`. Only the exact kink was wrong, and the existing boundary test used `r = 0.05, q = 0`,
which is not at the kink — so the case was never covered.

## 2026-07-29 — The degenerate test is on `sigma sqrt(T)`, not on `sigma` and `T` separately

`volatility === 0 || timeToExpiry === 0` misses the case where both are strictly positive and
their product underflows. At `volatility = 5e-324` with `timeToExpiry = 0.25` the deviation rounds
to 0, `d1` becomes `0 / 0 = NaN`, and that propagated into every price and Greek — a `NaN` from a
library whose stated contract is that it never returns one.

Every degenerate branch now routes through one shared predicate, `hasNoDispersion`. Underflow is
not a separate case from zero; it is the same case reached by arithmetic rather than by input.

## 2026-07-29 — Round two, and what a second review pass was worth

The five defects from round one were fixed and committed without the review being run again. That
gap was raised in critique, the review was re-run against the fixes, and it found **four more** —
two of them created or left standing by the round-one fixes themselves:

1. **Vega at the kink**, above. A defect in the original code that round one did not look for.
2. **The binomial representability guard refused puts.** The guard was added by the round-one fix
   for the `Infinity` defect. Its reasoning is call-specific — a call payoff at an overflowed node
   is `Infinity`, a put's is `max(K - Infinity, 0) = 0`, which is correct — but it was applied to
   both. It therefore rejected put trees that computed correctly, for inputs inside the documented
   domain, and did so exactly when the caller raised `steps` for accuracy. A fix that reproduced
   the failure mode it was written to remove.
3. **`maxRepresentableSteps` named a step count that also fails.** `Math.max(1, ...)` turned a
   limit of 0 into 1, contradicting the helper's own documented contract. Also introduced by the
   round-one fix.
4. **`parametricVar` returned `-0`.** Round one hardened `toLosses` and stopped there. Worse, the
   sweep added in round two to prove the class was closed used only confidence levels at or above
   0.5, where the quantile is non-negative — so a file whose stated claim is that the rule is
   checked _everywhere_ missed it.

Writing the regression tests then surfaced a fifth, the `sigma sqrt(T)` underflow above.

**What this says.** A fix carries the same blind spot as the code it repairs, because it comes
from the same model. Two of the four new defects existed only because of the previous round's
fixes. The rule that follows is in CLAUDE.md: run the verifier _after_ fixing, not only before.

It also says something about coverage. The suite stood at 98.65% statements and 97.4% branches
when the first five defects were found, and every one of them was in a covered line. Coverage
measures execution, not correctness. It earned its keep exactly once, on `maxRepresentableSteps`,
where an uncovered branch was a real defect in new code — worth running, worth not trusting.

## 2026-07-30 — The boundary values are limits, not conventions; this supersedes both earlier entries

Two earlier entries called the boundary Greeks conventions: the first said delta at the kink is
"the midpoint of the subgradient... the conventional choice", the second corrected vega but left
the framing intact. **Both were wrong about what these numbers are**, and the framing mattered
more than either error.

Measured, approaching the kink from inside the domain:

```
delta at S = K, r = q = 0, as T -> 0+       delta at the forward, r = q = 0.05, as sigma -> 0+
  T=1        0.539827837277029                 sigma=0.5     0.5695070736243045
  T=1e-2     0.5039893563146316                sigma=1e-3    0.47580445506034863
  T=1e-8     0.5000039894228039                sigma=1e-8    0.4756147141477853
  T=1e-12    0.5000000398942281                sigma=1e-20   0.475614712250357
  T=0        0.5                               sigma=0       0.475614712250357
```

The right column converges on `0.5 e^(-0.05) = 0.475614712250357` and the boundary branch returns
exactly that, bit for bit. Nothing is being chosen. At the kink `spotTerm = strikeTerm` forces
`d1 = sigma sqrt(T) / 2 -> 0`, hence `N(d1) -> 1/2`.

**The rule, which replaces five separately recorded conventions:**

> Report the limit of the analytic formula approached from inside the domain. Where that limit
> does not exist finitely, report 0.

Gamma at the kink is the only place the second clause applies — measured, it diverges as `1/sigma`
(3.8e0 at `sigma = 1e-3`, 3.8e9 at `sigma = 1e-12`), while theta converges to 0 linearly
(−1.76e-2 to −1.76e-11 over the same range) and delta, vega and rho converge to their reported
values.

**Why this is worth an entry of its own.** A list of conventions decides nothing about the next
case; a rule decides all of them. Vanna, charm, volga and speed already have their boundary
behaviour determined. And the rule is enforceable, which a convention is not: `boundaryGreeks` and
the analytic branch must agree in the limit, so a defect in either shows up as a discontinuity in
the library's own output. That is precisely how vega was caught. The property test in
`blackScholes.property.test.ts` now checks it over the whole domain.

The full statement lives in `docs/MATH.md` §6.2 and is not restated elsewhere. Five copies of a
convention are how the previous version drifted.

## 2026-07-30 — The Black-Scholes PDE, as a machine-enforced check on the theta convention

```
theta + (1/2) sigma^2 S^2 gamma + (r - q) S delta - r V = 0
```

Now tested, deterministically and as a property over the documented domain. Worst relative
residual measured: **1.0e-14**.

Two things this buys that nothing else in the suite did.

It is the first check that constrains `theta`, `gamma`, `delta` and the price **simultaneously**.
Every other Greek test checks one output at a time — against a finite difference, against Hull,
against its own sign convention — and four individually plausible values can all be wrong
together. This identity is not satisfiable by accident.

And it turns the unit convention from a promise into an invariant. Per-year is the unit in which
the identity holds without a conversion factor: with theta expressed per day the same residual is
5.08, 4.55 and 1.10 at three ordinary contracts. Anyone changing theta's unit now breaks a test by
a factor of 365 rather than quietly making the documentation wrong. That is the difference between
a convention that is written down and one that is held in place.

## 2026-08-01 — The tail accuracy figure was a measurement artefact; this supersedes "2.4e-16"

The entry above on deviating from West's constants reports the worst relative error above the
branch point as **2.4e-16**, and `docs/MATH.md` §3.4 repeated it. **That figure is wrong, and the
way it was wrong is the part worth recording.**

It was measured at the reference fixture points. Those points are integers and half-integers,
because those are the values a person writes down when choosing test inputs. For exactly those
`z`, `z^2/2` is exactly representable as a double. And `z^2/2` is the argument to
`Math.exp(-z*z/2)`, where

```
d(exp(-u)) / exp(-u) = -du
```

so any rounding of the argument passes through as relative error in the result. The measurement
was therefore taken on precisely the measure-zero set where this error term vanishes, and the
result was reported as holding _anywhere on the line_.

Measured on a dense sweep with exact BigInt comparison, the worst relative error is **5.2e-15 at
z = 11.6**, twenty-two times the figure claimed, and it follows the envelope `(z^2/2) * eps`:
8.9e-16 on [3, 5), 7.1e-15 on [8, 12), 5.7e-14 on [30, 38). The mechanism predicts the data rather
than fitting it — where `u` is exactly representable the error drops back to ~1e-16, and where it
is not it tracks `|du|` digit for digit. The full tables are in `docs/MATH.md` §3.4.

The corresponding figure inside Hart's branch was also slightly optimistic: 1.2e-14 claimed,
1.4e-14 measured at z = 2.98, in the location the entry above already identified correctly.

**What is unaffected.** The decision to deviate from West stands entirely. West as published is
~1e-9 across this range; the floor here is ~1e-14. The deviation still buys five to seven orders
of magnitude, and every number in the comparison table of the entry above reproduces exactly. Only
the summary figure for the shipped implementation was wrong.

**The lesson, which generalises past this library.** Twice now the project's own measuring
instrument has been the defect rather than the thing measured — first the reference generator's
working precision, where too few digits produced a number that was wrong by 3.5e-4 while still
looking like a number, and now the choice of measurement points. Both were wrong answers that
looked like answers.

The common cause here has a name: **convenient test points are systematically optimistic.** The
values that are easy to write down — integers, halves, round decimals — correlate with being
exactly representable, and exact representability correlates with floating point behaving at its
best. A test grid chosen for legibility is a test grid chosen, without anyone intending it, for
flattery.

This is the third instance of the same shape in the documentation: a probe presented as a limit
(§6.2, corrected 2026-07-30), a single contract presented as a function of scale (§9, corrected
2026-08-01), and now a favourable subset presented as a claim over the whole line. The pattern is
recorded in `.claude/agents/quant-verifier.md` as a boundary check of its own.

**Declined, and recorded so it reads as a decision rather than an omission.** Computing `z^2/2` in
double-double arithmetic would restore ~1e-16 relative accuracy throughout. It is not implemented
because the **absolute** error is unchanged by it, and absolute error is what pricing consumes —
`N` always enters multiplied by `S` or `K`. Same standing as log space for the binomial tree.

**And the performance claim was never measured.** The entry above says the deeper continued
fraction "costs about 60 divisions on a branch that only deep out-of-the-money inputs reach", and
MATH.md said the cost was nil. Measured: 19.2 ns against West's 17.0 ns inside Hart's branch
(1.13x), and **157 ns against 19.9 ns on the tail branch — 7.9x**. That is still 6.4 million calls
per second against a whole `bsCall` at 72 ns, so the conclusion holds and the CDF is a bottleneck
nowhere. But "nil" was an assertion, and it is now a figure a reader can reproduce.

## 2026-08-01 — Three figures in the Hart/West entry were wrong; this supersedes them

The entry of 2026-07-29 on choosing Hart/West over Abramowitz & Stegun contains three measured
numbers that do not reproduce. All three are corrected here rather than edited there.

**1. Put-call parity under A&S: 1.8e-12 claimed, 1.0e-5 measured.** Seven orders of magnitude, and
the mechanism is exact. A&S 26.2.17 evaluates its upper tail at `z = 0` as `0.5 - 5.25e-10` rather
than `0.5`, because its coefficients sum to 1.253314136 where `sqrt(pi/2)` is 1.2533141373155003.
The reflection `N(x) = x >= 0 ? 1 - Q(x) : Q(-x)` is exact for every `x` except **zero itself**,
where both branches take the `x >= 0` path and the error does not cancel. So at any contract with
`d2 = 0` exactly, parity fails by `strikeTerm * 1.05e-9` — 1.0e-5 at `S = K = 10 000`.

The measurement grid behind the original figure never contained such a contract. The corrected one
did, and only by coincidence: it happened to include `r - q = 0.02` alongside `sigma = 0.2`, and
`sigma^2 / 2 = 0.02` puts `d2` exactly on zero.

**The decision is not weakened by this; it is better founded.** The entry concluded that "the
ordering between them is noise", and that sentence is now false. Hart/West is not merely more
accurate in the tail — it is structurally safe at `d2 = 0`, where A&S's reflection breaks, because
`normalCdf(0) === 0.5` holds exactly here and the identity `N(0) + N(-0) = 1` is bitwise.

**2. `N(-10.4)` is 1.240e-25, not 1.04e-25.** A 19% error, in the round-one entry describing the
complement defect. The conclusion — that `1 - N(d2)` returns a hard 0 where the direct tail returns
a representable number — is unaffected.

**3. Gamma "returns 3.99e297 just above the boundary".** 3.99e297 is the value at
`sigma = 1e-300`. At the boundary proper — `sigma = 5e-324`, the smallest denormal — gamma is
`Infinity`. Which strengthens the argument for reporting 0 rather than weakening it.

**Why this entry matters more than the three corrections in it.** Number 1 is the same defect as
every other one found in this review: a grid chosen for legibility, missing the degenerate point.
It occurred **in the entry that establishes the library's thesis** — the document whose purpose is
to show that this project measures rather than asserts. Number 2 is a 19% recall error in the entry
whose own stated lesson is that "several values recalled from memory during initial drafting were
wrong in the last one or two digits. That is the reason this generator exists."

That is not irony, and it is not carelessness. It is evidence that **the pattern is stronger than
awareness of it**. Knowing that convenient numbers are dangerous does not stop anyone writing them
down. Only measuring does.

## 2026-08-01 — A ten-question review of the documentation, and what the ratio says

Every convention in `docs/MATH.md` and `README.md` was worked through as ten questions a quant
would ask, each answered by measurement rather than by reading. The result: **sixteen defects, and
all but one of them in the claims rather than in the code.**

Recorded because the ratio is the finding. Across two earlier rounds, adversarial review of `/src`
produced nine defects in the mathematics. This pass produced sixteen in the description of that
mathematics — while the code itself needed exactly one behavioural change, to an error message.

**The code held. What was written about the code did not.** Prose has no test suite, and that is
where the risk sits.

### The two patterns underneath

**Convenient points and convenient special cases.** Seven instances. The reference fixtures are
integers and half-integers, which is exactly where `z^2/2` is exactly representable, so the tail
accuracy figure was measured on the measure-zero set where the error vanishes. §6.2's boundary
table used `r = q = 0.04` and `S = K = 100` — three degeneracies at once, one of which made theta's
limit 0 by coincidence and hid that it is `(q - r) spotTerm / 2`. §9's parity table was one
contract presented as a function of scale. The VaR square-root-of-time rule is exact only at zero
drift. And the A&S parity figure above.

The root is a single sentence: **simplicity in notation correlates with degeneracy in the
mathematics.** The values a person writes down are the values at which floating point behaves best
and at which terms cancel. A grid chosen for legibility is a grid chosen, unintentionally, for
flattery.

**Recipes that outlive the fix.** Four instances, and this class is worse per occurrence, because
the error migrates into the reader's code where nothing here can catch it. `1 - N(d2)` was removed
from the source in round one and survived in a JSDoc block as advice to callers — wrong at the
degenerate kink, and discarding 7.5e-21 as a hard 0 deep in the money. §6.2 taught a convergence
probe at `sigma = 1e-12`, past the point where the sequence turns around. `crrPrice` told callers to
"increase steps" where no legal step count exists, and to "use the analytic pricer", which returns
0.00 for an American put worth 60.00 — while its sibling message twelve lines away was correctly
qualified. And the README promised no `NaN` unconditionally while the property test behind it drew
only from the documented domain.

The root here is different: **correct knowledge existed in the repository and failed to travel.**
The same shape as the `-0` guard that was applied in `boundaryGreeks` and not in `historicalVar`.

### The method that worked, and is now in the verifier

- **Try to refute the document's own claim, and design the experiment so it can succeed.** Two CDFs
  with identical 7.45e-8 error, one with a consistent reflection and one without: parity perfect in
  the first, broken 2000-fold in the second. That is a proof, not an illustration.
- **Mutation testing for coverage gaps.** Implementing the wrong claim — theta forced to 0 at the
  kink — passed all 176 tests, eight runs out of eight, while a broader mutation failed at once.
  Reading produces a hypothesis; mutating produces evidence.
- **Sweep a product of extremes, not a list of them.** `gamma` is `NaN` at `S = 1e-320` with
  `sigma = 1e-320` while either alone is harmless. One parameter at a time is blind to this by
  construction.
- **State mechanisms, not figures.** A number is falsified by the next measurement; a mechanism
  explains all of them and lets the reader check their own case. The tail floor is now
  `(z^2/2) eps`, the per-day PDE failure is `0.9973 |theta|`, and the unusable tree region is
  `sigma < |r - q| sqrt(T / 20000)`.

### What changed in the code

One behavioural change: `crrPrice`'s risk-neutral-probability error now computes the step count
that would be needed, says plainly when that exceeds the cap, and qualifies the `bsPrice` fallback
to European contracts. Everything else was documentation, JSDoc and tests. The suite went from 175
to 179, coverage stayed at 100% of statements, branches, functions and lines.

## 2026-08-01 — The verifier's first run in its own right, and two real code defects

`quant-verifier` had never been run as a registered subagent — only through a general-purpose
agent, and never with the four checks added earlier today. Run against `/src` in a fresh context,
it produced nine findings. Every one was reproduced independently before being acted on.

**Two are defects in behaviour, not in prose.**

**1. `minimumStepsForValidProbability` was off by one, and the test written to prevent exactly
that could not see it.** The guard accepts `p <= 1`, so the requirement is `n >= T(|r-q|/sigma)^2`
and the answer is `ceil`, not `floor(x) + 1`. The two forms differ only when the ratio is an exact
integer — and all three worked examples in `docs/MATH.md` §5.1 are exact integers, so the error
message said 62 501, 625 001 and 25 001 where the documentation said 62 500, 625 000 and 25 000.
At `S = K = 100, r = 0.25, q = 0, sigma = 0.125, T = 1` the ratio is exactly 4 and `steps: 4`
prices at 22.1199, while the caller was sent to 5.

The test that was supposed to catch this used `sigma = 0.02`, where the ratio is 1562.5. **On a
non-integral ratio `floor + 1` and `ceil` agree.** A convenient test point, chosen the same day the
pattern was written up, in the test written to guard against it. The suite had also locked the
wrong value in as a string assertion.

This is the eighth instance of the pattern, and the clearest evidence yet for the note in the
entry above: knowing about it does not prevent it.

**2. `impliedVolatility` could return a volatility that missed `priceTolerance`, silently.** The
early return when the bracket collapses to the resolution of a double handed back the midpoint
without checking the residual. At `S = K = 10 000, T = 1, r = 0.05` with `priceTolerance = 1e-14`,
32 of 40 consecutive ulps of the target price returned without an exception and outside tolerance,
the worst by 205x. The module's stated guarantee — "never returns a number that does not reproduce
the input price", and §7.2's "failure is always an exception" — was unqualified and untrue. The
residual is now checked, and a tolerance finer than the price can represent is reported as a
`ConvergenceError` naming the mechanism.

**The remaining seven were wrong numbers**, and their shape is by now familiar:

- The Hart-branch worst error was quoted as 1.4e-14 at z = 2.98, from a sweep at step 0.02. Dense
  measurement gives 1.6e-14 rising monotonically into the branch point — the maximum is the limit
  at 3, not a grid point.
- Two of the five "awkward" fixture points added earlier today were not awkward. `z = 6.75` is
  27/4, so `z^2/2 = 22.78125` is exact in binary and `|du|` is 0 — a member of the very
  measure-zero set the point was chosen to avoid. Replaced by 4.87 and 6.83, each verified rather
  than assumed.
- `Q(37)` is **eight** orders of magnitude above the smallest normal double, not four, and a
  cutoff at 37 discards about **twenty-four** orders, not nineteen. Both figures appeared in four
  files.
- `1.04e-25` appeared in three places as the value of `N(-d2)` at three different contracts. It is
  right at none of them: at `d2 = 10.4` the value is 1.24e-25, and at the strike-60 contract in
  `test/risk.test.ts` it is 2.97e-25 with `d2 = 10.32`. One remembered number, copied twice.
- The relative accuracy quoted alongside it, 1.6e-16, is the superseded figure from this morning —
  corrected in four files and left standing in two.
- The kink table in `analytical.ts` gave a delta no input produces: its `vega` and `rho` rows are
  the analytic branch at `sigma = 1e-7`, but its delta row is neither that (0.4803947387) nor the
  boundary value (0.4803947196).
- `bsCall`'s own `@example` gave 4.759422392871542; the function returns ...535, which is the value
  the README and the `impliedVolatility` example both use.

**What the run says about the verifier itself.** Three of its four new checks fired. Mutation

Tests 179 -> 180, coverage still 100% on all four metrics.

## 2026-08-01 — Second verifier run: the fix for the fix was also wrong

`quant-verifier` was run again against the fixes from the run above, on the principle that made
round two necessary in July. It found nine more things. **Three were defects in behaviour, and two
of those were introduced by the previous fix.**

**1. The step-count advice was wrong in the other direction.** Replacing `floor(x) + 1` with
`ceil(x)` corrected the integral-ratio overshoot and introduced an undershoot: `crrPrice` began
advising a count that it then refused. At `S = K = 100, T = 0.25, r = 0, q = 0.15, sigma = 0.025`
the message said "raise steps to at least 9" and 9 throws; 10 prices at 3.6806. A caller following
the advice in a loop never terminates.

The cause is that the bound is exact in real arithmetic and `p` is not computed in real
arithmetic. When `q > r` the numerator compares `exp(-a)` against `1 / exp(a)`, which differ by an
ulp, so `p` lands at -1.3e-14 rather than 0 and the guard refuses it. When `r > q` both sides come
from `exp(a)` with the same argument, `p` is exactly 1, and every sweep of positive drift sees
nothing. **The test added with the previous fix used `r = 0.25, q = 0.15` — positive drift again.**

Then the sweep written to catch that found a third case, in the opposite direction: at
`r = -0.02, q = 0, sigma = 0.001, T = 0.04` the ratio is exactly 16 in real arithmetic and
16.000000000000004 as a double, so `ceil` says 17 while 16 prices. The bound can be wrong by one
either way.

The helper no longer trusts a closed form. It computes the bound, then verifies candidates against
the same expression the guard evaluates, starting two below and stopping eight above. Both
mutations — disabling the verification, and starting the search at the bound rather than below it
— now fail the suite.

**2. `impliedVolatility` refused prices it can reproduce exactly.** The bracket-collapse test was
`high - low <= 4 * eps * max(1, high)`. Every ordinary volatility is below 1, so the `max` made
the threshold an absolute 8.9e-16 and stopped the bisection roughly 1e5 ulps early. While the
branch returned silently this produced a slightly wrong answer; once the previous fix made it
throw, it became a refusal: at `S = K = 10 000, T = 1, r = 0.05` the solver declined
`sigma = 0.058` at a tolerance of 1e-12, claiming a bracket 98 000 doubles wide was "the
resolution of a double". 47 of 200 exactly-reproducible targets were refused at 1e-13.

**A guard added to fix one defect that then rejects valid input is the exact shape of round two's
second finding**, where the binomial representability check refused puts. The criterion is now
relative — `4 * eps * high` — and both sides of the collapse branch are tested.

**3. `bsCall` and `bsPut` returned negative prices inside the documented domain.** Pre-existing,
and the most serious finding of either run. At `S = 5000, K = 2, T = 5, r = 0.15, sigma = 0.1` the
put returns -1.102e-320. A European price is non-negative by no-arbitrage; the analytic branch is a
difference of two products that can both be subnormal, where the subtraction keeps only a handful
of bits. Measured rate inside the domain: about 23 calls and 30 puts per 500 000 draws.

Nothing caught it. The no-arbitrage bound test has a slack of `1e-9 * max(1, spotTerm, strikeTerm)`,
which a violation of -1e-320 disappears into completely — a tolerance chosen for the scale of
ordinary prices, applied to a quantity that is not of that scale. Both exits are now clamped at 0,
and a sweep of 7 200 in-domain contracts asserts it.

**The remaining six were wrong numbers or wrong prose**, including two more of the kind this review
keeps producing: the replacement fixture point `-4.87`, added hours earlier to demonstrate the tail
floor, has a relative error of 5.7e-16 and would have passed the strict tolerance it was supposed
to exceed; and the note warning against probing below `sigma = 1e-8` was attached to the one
contract where no such turnaround happens, because `ln(S/K)` and `r - q` are both bitwise zero
there.

### What this run settles about when to stop

Three rounds now, and the shape is stable: each finds fewer defects in the mathematics and more in
whatever was written last. Rounds one and two found nine defects in `/src`. The ten-question review
found sixteen, fifteen of them in claims. This pair of verifier runs found eighteen, five of them
in behaviour and three of those introduced by the review itself.

It does not converge to zero. It converges on **the newest layer** — the defects are always in what
was written most recently, however carefully the older material was checked. So the stopping rule
cannot be "no defects remain". It has to be that the defects still being found are cheaper to fix
after publication than to hunt for before it, and that judgement is now the only thing left open.

asserting, repeated by the author who wrote that subject down.

## 2026-08-02 — `private: true`, so that publication cannot happen by accident — TEMPORARY

> **Status: temporary.**
> **Trigger to remove: an explicit decision to publish, from Rabi, and nothing else.**
> Removing it is one line. It is not a chore to be tidied up by whoever notices it next.

`package.json` carries `"private": true`, which makes `npm publish` and `pnpm publish` refuse to
run. On a library whose entire purpose is to be published this looks like an error, so it is
recorded here as a decision.

**Why a flag rather than an intention.** Publication is irreversible in the way that matters: a
version number, once taken on npm, cannot be reused even after an unpublish, and the tarball is
mirrored within seconds. Every other guard in this repository is of the same kind — the API takes
named parameters so spot and strike cannot be swapped, the Greeks have no runtime unit setting so
a scaled number cannot be mistaken for an unscaled one. In each case a failure mode is closed in
the mechanism rather than left to care. This is that principle applied to the one action that
cannot be taken back.

**What it does not do.** It blocks nothing else. `pnpm build`, the full test suite, `npm pack` and
the CI workflow all run unchanged, so the publishable artefact stays continuously verifiable while
the act of publishing stays locked.

The state to be in is one where the only thing standing between the library and npm is a decision,
not a chore. That is now the case: the repository is publication-ready, and the flag is the record
that the decision has not yet been made.

**One thing to know on the day it is removed.** `npm publish --dry-run` does **not** exercise this
guard. `lib/commands/publish.js` calls `libnpmpublish` only under `if (!dryRun)`, and the check
lives inside that module — so a dry run against a private package packs the tarball, prints
`+ strikemath@0.1.0` and exits 0, which is indistinguishable from the flag not working. Verified
by calling `libnpmpublish.publish()` directly with this manifest: it throws `EPRIVATE` before any
network call. The flag works; the obvious test of it does not.

## 2026-08-02 — What ships in the tarball: the reasoning ships, the strategy does not

The published package contains `dist`, `README.md`, `LICENSE` and three of the four files in
`docs/`. Twelve files, 152 kB packed. Each part of that is a decision.

**`docs/MATH.md` and `docs/DECISIONS.md` are included, because they are the differentiator.** They
are the reason to choose this library over another one that also multiplies `N(d1)` by a discount
factor. Measured, the cost of leaving them out was concrete rather than theoretical: README links
into `docs/` **seven times**, and every one of those links was dead in the published package —
dead precisely where a developer follows it, in `node_modules`, having just been told the numbers
are checkable. `docs/` is 110 kB, which took the tarball from 112 kB to 152 kB.

**`docs/ROADMAP.md` is excluded, because it is planning rather than documentation.** It contains
the pricing model, the white-label positioning and what is deliberately not being built. A
competitor installing the package should not get the business plan with it.

**The exclusion is written as an allowlist, not as a negation pattern.** `!docs/ROADMAP.md` would
have closed the hole for the one file known about today and left every future internal document

mode beyond reach rather than relying on someone remembering. The cost is real and is accepted —

component. They are kept for the same reason the documentation is: a library that asks to be

verifiability is not weight this project economises on.

Both decisions point the same way, which is why they are recorded together: transparency over
slimness, consistent with every other choice in this repository.

## 2026-09-24 — Historical CVaR weights a fractional tail; this replaces `ceil((1 - c) n)`

`historicalCvar` averaged the worst `ceil((1 - c) n)` losses. It now averages the worst
`(1 - c) n` losses with the one straddling the edge of the tail counted by the fraction that lies
inside it — the estimator of Acerbi and Tasche (2002) — with two numerical safeguards described
below. When `(1 - c) n` is an integer `k`, the result is the mean of the worst `k`.

**The defect.** `1 - c` is not exact in binary. `1 - 0.95` is 0.050000000000000044, so at
`n = 20` the product is 1.0000000000000009 and `ceil` returns 2. Measured by running the function,
the old estimator averaged one loss too many at exactly the sizes people use:

| `n`  | `c`   | Intended tail | Used |
| ---- | ----- | ------------- | ---- |
| 20   | 0.95  | 1             | 2    |
| 100  | 0.99  | 1             | 2    |
| 500  | 0.99  | 5             | 6    |
| 1000 | 0.99  | 10            | 11   |
| 1000 | 0.975 | 25            | 26   |

Swept over every `n` from 2 to 400 and every `k` below it, with `c = 1 - k / n`: **14 037 of
79 800 pairs took the wrong tail.** The existing test sat at `n = 10, c = 0.9`, where the product
rounds _down_ to 0.9999999999999998 and `ceil` is right by luck — the convenient-point pattern this
log has been recording since 29 July, once more.

**Why the fractional estimator, rather than a tolerance on `ceil`.** `ceil(m - 1e-9)` would have
fixed the table and left the estimator discontinuous: every time the tail gains an observation the
result jumps, by up to half the gap between two losses. The fractional estimator is continuous in
`c` and is the form under which expected shortfall is coherent on an empirical distribution, which
is the property the module's own header gives as the reason to prefer CVaR over VaR.

### The first two versions of this fix were wrong, and the verifier found both

Written and tested, the fractional estimator was run past `quant-verifier` before commit, on the
rule that fixes carry the blind spot of what they repair. Then the fix to its findings was run past
it again, on the same rule. Every finding was reproduced independently before being acted on.

**Round one** found three defects in the fix and four false claims in its documentation.

1. **The fraction only shrank the excess.** `m = 1.0000000000000009` became a weight of 8.9e-16 on
   `L_2` instead of a whole extra observation, and the first draft of this entry said that "cannot
   move the result". It can: with the worst loss at 0 and nineteen gains of 1 the answer was
   -8.9e-16 rather than 0, and with the worst at 1e-300 among gains of 1e300 it was -8.9e284. A
   small weight on a large gain moves a result near zero by an unbounded relative amount.
   **Fix:** `m` within `2 n eps` of a whole number is taken to be that number — how precisely `m`
   is known at all, with the worst error measured at `0.75 n eps`.
2. **Underflow at `m < 1`:** `fraction * loss / m` sent a loss of 1e-310 to 0 at `n = 1`.
3. **Overflow**, pre-existing: summing the tail before dividing gave `-Infinity` on two gains of
   1e308. The fix for 2 and 3 was to divide each loss by `m` before adding it, on the argument that
   the weights sum to 1 and so every partial sum stays inside the range of the losses.

**Round two** found that argument true only in exact arithmetic, and that the fix had traded one
end of the range for the other.

4. **Still overflowing.** In floating point the weights sum to a hair over 1: `n` losses of
   `Number.MAX_VALUE` returned `Infinity` for 456 of the sizes from 1 to 1000, and three losses of
   1.79e308 returned 1.7900000000000002e308, above every loss. The test used two losses of 1e308,
   where no size overflows — a convenient point in the test written for this very fix.
5. **A new underflow, a regression from the code being replaced:** dividing each loss by `m` sent
   two losses of 5e-324 at `m = 2` to 0, where `ceil` had returned 5e-324 exactly. The test covered
   only `m < 1`.
   **Fix for 4 and 5:** the sum is taken in units of a power of two near the largest loss — exact
   to divide by, every term at most 2, so nothing overflows and nothing subnormal underflows — and
   the result is held to the range of the losses it averages, which it cannot leave in exact
   arithmetic and can by an ulp in floating point.

The false claims, across both rounds, corrected in the source, MATH §8.3 and the tests:

- that `CVaR >= VaR` holds **always** — it holds in exact arithmetic, and in floating point to
  within the rounding of a sum of up to `n` terms. Round one's correction said "a few ulps of the
  largest loss", which round two measured at 2176 ulps on 10 000 flat losses, on that round's code;
- that no distinguishable input is snapped — at `n = 20`, 0.95 and the seven doubles around it are
  all read as 0.95. What does hold: a confidence level of six or fewer decimals is at least 1e-6
  from a whole tail mass, against a bound of at most 4.4e-10 for `n` up to a million;
- that the stray weight grows with `n` — the figure quoted was the excess `m - k`, not the weight
  `(m - k)/m`, which is 8.5e-16 at `n = 1000`, smaller than at `n = 20`;
- that the estimator moves by at most the step in `c` — its Lipschitz constant is
  `n |L_(k+1) - CVaR| / m`, 1000 on one loss among 999 zeros;
- that integral cases change "nothing beyond the last digit" — they change by a whole observation,
  which was the point;
- and two test comments: a continuity figure off by a factor of two, and a `-0` test that could
  not fail, because its input turned `-0` back into `+0` before the exit guard was reached.

**The tests that were meant to prove the fixes could not see the defects.** The sweep over every
`(n, k)` uses evenly spaced losses, where a stray weight of 1e-15 moves the mean by less than the
summation rounding: it passed with and without the snap, 21 eps either way. A second sweep puts
the worst `k` losses at exactly 0 among gains, so any stray weight shows; without the snap it
fails at exactly the 14 037 pairs `ceil` did. Round two then showed that rounding `m` to the
nearest whole number outright — a snap threshold of 0.49 — survived the whole suite, because the
only fractional test point was 1.5, where rounding ties. Tests at 1.3, and at genuine distances of
1e-6 and 1e-12 from a whole number, now pin it.

**Verified to have teeth**, each safeguard separately, in a battery of fifteen mutants: restoring
`ceil` fails seven tests; removing the snap, the range check, the scaling or the `-0` guard each
fails at least one; snap thresholds of 0.49, 1e-3 n, 1e-6, 1e-9 and `2 eps` all fail. Two of the
fifteen survive and are harmless: a threshold of `n eps`, still above the measured error of
`0.75 n eps`, and `floor` for the nearest whole number, which leaves a tail mass just below a
whole number unsnapped — harmless because the leftover weight then falls on a loss inside the tail,
not outside it. A threshold of 1e-13 also survives, tried separately: the suite pins the threshold
between the measured error and the closest genuine distance it tests, 1e-12, and no tighter.
Tests 184 -> 192, coverage 100% on all four metrics.

**What changes for a caller.** Where `(1 - c) n` is meant as a whole number, the result is now the
mean of that many losses, where `ceil` often took one more. Where it is not, the result is a
weighted average between the two neighbouring counts — at `n = 10, c = 0.85` it moves from 0.045 to
0.0467. At the ends of the double range, where the old estimator returned `Infinity`, it now
returns the mean.

**On when to stop.** The entry of 1 August predicted this: review converges on the newest layer,
not on zero. Two rounds on a single function found five behavioural defects: three created by the
fixes, one the fix claimed to close and did not, and one that predates this work. The stopping rule
stated there still applies and is Rabi's to apply. For that judgement: round two's behavioural
findings sit only at the extremes of the double range, and the rest of what it found was in the
claims.

- A fresh `npm install strikemath` in an empty directory, then Hull example 13.6 through both
  entry points: ESM `import { bsCall }` and CJS `require('strikemath')` each return
  4.759422392871535 — the value in the README and in `test/hull.bench.test.ts`.
- The installed package holds the twelve files the allowlist names, 162 kB packed; `docs/` is
  present, so the README's seven links into it resolve.
- `gh repo view --json isPrivate` → `false`; `refs/tags/v0.1.0` is on the remote.

**What was learned on the way, recorded so the next release does not rediscover it.**

1. **`npm publish` succeeding is not proof of publication.** The publish was staged: npm first
   created a placeholder version `0.0.0-stage` and held `0.1.0` until it was approved on
   npmjs.com, about ninety seconds later. Between those two moments the CLI had reported success
   and the registry served no `0.1.0`. The check that settles it is `npm view <pkg> version`, and
   it is the same class of distinction this log has drawn before: the command describes an
   intention, the registry describes what is.
2. **The placeholder is public.** `0.0.0-stage` remains listed in `npm view strikemath versions`,
   332 bytes unpacked and installable by explicit version. `latest` does not point at it, so no
   ordinary install sees it. Whether to deprecate it is a decision for 0.1.1 and is on that
   backlog in STATUS; deprecation is reversible, unpublish is not.
3. **`npm publish --auth-type=web` from WSL needs `BROWSER=echo`.** Without it the CLI tries to
   open a browser that does not exist inside WSL; with it the login URL is printed and opened by
   hand on the Windows side.
4. **Provenance was not generated**, as expected: the publish ran from a laptop, not from a
   workflow, and the repository was still private when the tarball was built. Trusted publishing
   from CI is the 0.1.1 route, and it will be the first release whose provenance a reader can
   check.

**What this entry does not change.** `docs/DECISIONS.md` stays append-only. The two
`.claude/settings.json` denials on `npm publish` and `pnpm publish` stay in place: with the flag
gone they are now the only mechanical guard, and the next release should go through a workflow
rather than through either command typed by hand.
