# Decisions

Append-only. Each entry records what was decided, when, and why. Entries are never edited or
removed — if a decision is reversed, a new entry supersedes it and says so.

## 2026-07-29 — Package name: `strikemath`

Final. Used consistently everywhere: `package.json`, README, docs, directory names, imports.

`volsmith` was the working name during earlier design work and was dropped for its adjacency to
Optionsmith, a live commercial product in the same vertical. `optionsmith`, `greeklab` and
`optionlab` were excluded for the same reason: each has an active namesake in options software.

## 2026-07-29 — Greeks are returned in raw units, and scaled only through named functions

The core always returns:

| Greek   | Unit                                               |
| ------- | -------------------------------------------------- |
| `delta` | per 1.0 of spot                                    |
| `gamma` | per 1.0 of spot squared                            |
| `vega`  | per **1.00 of volatility** — 100 volatility points |
| `theta` | per **year**                                       |
| `rho`   | per **1.00 of rate**                               |

Scaling happens exclusively through `greeks/scaling.ts`: `vegaPerPercentagePoint`,
`thetaPerCalendarDay`, `thetaPerTradingDay(theta, tradingDaysPerYear = 252)`,
`rhoPerPercentagePoint`. There is no runtime-configurable scaling and no units option object.

**Why.** A scaled number is indistinguishable from an unscaled one. `theta = -4.31` could be per
year or per day, and with a configurable unit the answer depends on a setting somewhere up the
call stack that the reader of the calling code cannot see. `thetaPerCalendarDay(theta)` cannot be
misread. The cost is one extra call; the benefit is that no returned number is ever ambiguous.

The convention is documented in three places: JSDoc on each function, the README, and
`docs/MATH.md`.

## 2026-07-29 — Normal CDF: Hart/West, not Abramowitz & Stegun 26.2.17

**The reason is absolute accuracy and nothing else.** A&S 26.2.17 carries a stated error bound of
|eps| < 7.5e-8 (measured here: 7.45e-8 at x = 0.718). Hart's rational form in West's
double-precision presentation is near machine precision. For a library whose entire premise is
that its numbers can be trusted, that difference costs nothing to take.

**Do not confuse accuracy with parity.** Put-call parity is a _structural identity_, not a
precision requirement. Algebraically it reduces to

```
C - P = S e^(-qT) [N(d1) + N(-d1)] - K e^(-rT) [N(d2) + N(-d2)]
```

so it holds to machine precision purely because `N(x) + N(-x) = 1`, no matter how accurate `N`
is otherwise. Measured over the documented domain: A&S gives 1.8e-12, Hart/West gives 3.6e-12 —
both far inside the 1e-9 tolerance, and the ordering between them is noise.

The consequence for debugging is the part that matters: **if a parity test fails, the fault is in
the reflection or in the input domain — never in the CDF's accuracy.** The reflection is therefore
implemented explicitly, with `normalCdf(-x)` and `1 - normalCdf(x)` computed from the same
upper-tail routine, so the identity holds by construction and a failure points at the right place.

The Hull benchmark is the opposite requirement: it tests absolute accuracy against published
values, not internal consistency.

## 2026-07-29 — Documented deviation from West's published constants

`normalCdf` uses Hart's rational form below |z| = **3** and a Laplace continued fraction of
**60 levels** above it. West (2005) publishes the branch point at 7.07106781186547 with a 5-level
continued fraction and a 0.65 terminator.

**Measured, against 40-digit ground truth** (`test/fixtures/normal-reference.json`, generated by
exact BigInt fixed-point arithmetic with pi from Machin's formula — no constant is taken on
trust):

| z   | Q(z)     | relative error, West as published | relative error, as shipped |
| --- | -------- | --------------------------------- | -------------------------- |
| 3   | 1.35e-3  | 1.5e-14                           | 0                          |
| 5   | 2.87e-7  | 4.6e-11                           | 1.8e-16                    |
| 7   | 1.28e-12 | 2.6e-9                            | 1.6e-16                    |
| 8   | 6.22e-16 | 8.7e-9                            | 1.6e-16                    |
| 10  | 7.62e-24 | 3.2e-9                            | 1.9e-16                    |
| 20  | 2.75e-89 | 1.7e-11                           | 2.5e-16                    |

Worst relative error anywhere on the line, as shipped: 1.2e-14, occurring just below the branch
point inside Hart's branch. Above the branch point: 2.4e-16.

**Why deviate at all.** West's published constants are tuned for _absolute_ accuracy and they
achieve it — around 1e-16 everywhere, which is what the decision above is about and which is
fully sufficient for pricing, where `N` enters multiplied by `S` or `K`. The published form's
_relative_ accuracy in the tail is the part that degrades, because the value itself has become
tiny.

The practical effect is small and is not claimed to be otherwise: at z = 7 the absolute error of
the published form is about 3e-21. The deviation was taken because the cost is nil, because the
tail branch is genuinely reached by 0DTE and weekly deep-out-of-the-money contracts where d2 sits
around -4.6, and because a deviation that is measured, documented and reproducible is an asset
for a library that sells itself on correctness.

**Constraints this decision carries.**

1. There is no runtime choice between the variants. The library ships exactly one normal CDF.
2. The reference values are permanent test fixtures, generated in exact arithmetic and
   regenerable with `node test/fixtures/generate-reference.mjs`.
3. West's published form is retained as a _comparison baseline_ in
   `test/normal.west-comparison.test.ts` — as a test, not as an option. That test also asserts
   that the published form satisfies its own claim of ~1e-16 absolute accuracy, so the comparison
   is fair rather than a straw man.
4. The deviation is written up here and in `docs/MATH.md`.

## 2026-07-29 — Greeks at the boundary report the limit, and the subgradient midpoint at the kink

When `timeToExpiry` or `volatility` is exactly 0 there is no randomness left, so the payoff is a
deterministic function of the discounted forward and the Greeks are its derivatives:
gamma and vega are 0, and delta, theta and rho follow from `max(S e^(-qT) - K e^(-rT), 0)`.

Two points are conventions rather than derivations, and are stated as such:

- Gamma's true limit at the strike is a Dirac delta, which has no finite value. It is reported
  as 0.
- Exactly at the kink the payoff is not differentiable. Delta is reported as the midpoint of the
  subgradient: 0.5 for a call, -0.5 for a put.

Out of the money every sensitivity is returned as literal `0` rather than `sign * 0`, so a put
never reports `-0` — which compares unequal to `0` under `Object.is` and would surprise anyone
aggregating Greeks across a position.

## 2026-07-29 — Monotonicity properties are asserted against a resolution floor

A Black-Scholes price is a difference of two terms of order `S` and `K`, so it carries an
absolute rounding of a few ulp of the larger. Where the true difference between two prices falls
below that, the computed ordering can invert.

Property tests therefore assert monotonicity with a floor of `8 * eps * max(S, K)`, and assert
_strict_ monotonicity only once the gap exceeds ten times that floor.

This is not a weakened assertion; it was verified rather than assumed. The counterexample that
prompted it — S = 28.8, K = 2.5144595332169533, T = 0.04176592831188112, r = 0, sigma 0.001 vs
1.515616632428247 — was re-evaluated in the cancellation-free form
`C - (S e^(-qT) - K e^(-rT)) = K e^(-rT) N(-d2) - S e^(-qT) N(-d1)`. The true increase is
**5.6e-16**, while one ulp of the price is **5.8e-15** — ten times larger. The price is genuinely
monotone in volatility; the ordering is simply not representable there.

## 2026-07-29 — Reference values are generated, not transcribed

Every expected value for the normal distribution comes from
`test/fixtures/generate-reference.mjs`, which computes in exact BigInt fixed-point arithmetic at
adaptive precision. Two details were found the hard way and are guarded in the generator:

- The working precision must exceed `x^2 / ln 10`, not `x^2 / (2 ln 10)`. Getting it wrong is
  silent: at x = 37 with 600 digits the result was wrong by 3.5e-4 relative while still looking
  like a number. The generator now cross-checks every value at two precisions and refuses to emit
  one where they disagree.
- Values are computed at the exact IEEE-754 double nearest the printed literal, not at the
  decimal literal. `4.6` is really 4.5999999999999996447..., and evaluating Q at the decimal
  instead shifts the result by 1.6e-15 relative — which would have been misread as an inaccuracy
  in the library.

Several values recalled from memory during initial drafting were wrong in the last one or two
digits. That is the reason this generator exists.

## 2026-07-29 — Five defects found by adversarial review, and what they had in common

An adversarial review of `/src` by the `quant-verifier` subagent found five real defects after the
test suite was already green at 146 assertions. All five are fixed and each carries a regression
test. They are recorded here because the pattern is worth remembering.

1. **`crrPrice` returned `Infinity`.** The highest terminal node is `e^(ln S + sigma sqrt(T n))`,
   which overflows for inputs inside the documented domain — `S = K = 100`, `T = 1`, `sigma = 5`,
   `n = 20 000`. A call payoff of `Infinity` propagated to the root. Worse, the failure appeared
   _when the caller raised `n` to get a better answer_: the same contract priced correctly at
   `n = 1000`. Now checked before any work is done, and refused with a message that says what to
   do instead.

2. **`probabilityItmUnderQ` reported an expiring at-the-money put as certain.** The degenerate
   branch returned `terminal > level ? 1 : 0`, and the put case was computed as `1 - above`. At
   `terminal === level` both strict inequalities are false, so both probabilities should be 0 —
   but the complement turned one of them into 1. The library simultaneously priced the put at 0
   and reported a certainty of finishing in the money.

3. **The put probability was `1 - N(d2)` rather than the documented `N(-d2)`.** Algebraically
   identical, numerically not: at `d2 = 10.4` the complement returns a hard 0 where `N(-d2)` is
   1.04e-25 — a representable number the CDF produces to 1.6e-16 relative accuracy. This one is
   the sharpest of the five, because it discarded, in a thin wrapper, exactly the tail accuracy
   that the deviation from West's constants exists to provide.

4. **`normalCdf` truncated the tail at |z| = 37.** The cutoff was justified in a comment by
   `1 - Q(z)` being indistinguishable from 1 beyond it — true, and irrelevant to `Q` itself, which
   stays representable to |z| ~ 38.5. Some nineteen orders of magnitude were being thrown away.
   The cutoff is gone; `Math.exp` underflows on its own where 0 is correct.

5. **`historicalVar` could return `-0`.** Negating a flat return produced `-0`, which compares
   unequal to `0` under `Object.is`. The identical hazard had already been identified and guarded
   in `boundaryGreeks` and was simply not applied here.

**What they had in common.** Four of the five sit at a boundary the tests exercised only from one
side: a strict inequality at the point of equality, a complement in the tail, a cutoff constant, a
signed zero. None was a wrong formula; every formula in the library was correct. The defects were
in the _transitions_ — between the continuous case and the degenerate one, between a representable
value and an unrepresentable one, between an identity that holds in exact arithmetic and its
behaviour in floating point.

A green suite says the cases you thought of pass. It says nothing about the cases you did not, and
the boundaries are where those live.

## 2026-07-29 — Vega at the kink is finite; this supersedes the earlier "gamma and vega are 0"

The entry above on boundary Greeks said gamma and vega are both 0 at the boundary, justifying it
with the Dirac-delta argument. That argument is correct for gamma and **wrong for vega**, and the
entry is superseded on that point.

At the kink — `volatility = 0`, `timeToExpiry > 0` and the forward exactly on the strike —
approaching from `sigma > 0` gives `d1 = sigma sqrt(T) / 2 -> 0`, so

```
vega -> S e^(-qT) sqrt(T) phi(0)
```

which is finite and large: **39.894** for `S = K = 100`, `r = q = 0`, `T = 1`. Reporting 0 put a
jump discontinuity into the library's own output — the analytic branch returns 39.894 at
`sigma = 5e-324` and the boundary branch returned 0 at `sigma = 0`. Gamma is different: it
genuinely diverges, and the code returns 3.99e297 just above the boundary, so 0 remains the only
finite thing to report.

Away from the kink vega really is 0, because the value approaches intrinsic exponentially fast in
`1/sigma^2`. Only the exact kink was wrong, and the existing boundary test used `r = 0.05, q = 0`,
which is not at the kink — so the case was never covered.

## 2026-07-29 — The degenerate test is on `sigma sqrt(T)`, not on `sigma` and `T` separately

`volatility === 0 || timeToExpiry === 0` misses the case where both are strictly positive and
their product underflows. At `volatility = 5e-324` with `timeToExpiry = 0.25` the deviation rounds
to 0, `d1` becomes `0 / 0 = NaN`, and that propagated into every price and Greek — a `NaN` from a
library whose stated contract is that it never returns one.

Every degenerate branch now routes through one shared predicate, `hasNoDispersion`. Underflow is
not a separate case from zero; it is the same case reached by arithmetic rather than by input.

## 2026-07-29 — Round two, and what a second review pass was worth

The five defects from round one were fixed and committed without the review being run again. That
gap was raised in critique, the review was re-run against the fixes, and it found **four more** —
two of them created or left standing by the round-one fixes themselves:

1. **Vega at the kink**, above. A defect in the original code that round one did not look for.
2. **The binomial representability guard refused puts.** The guard was added by the round-one fix
   for the `Infinity` defect. Its reasoning is call-specific — a call payoff at an overflowed node
   is `Infinity`, a put's is `max(K - Infinity, 0) = 0`, which is correct — but it was applied to
   both. It therefore rejected put trees that computed correctly, for inputs inside the documented
   domain, and did so exactly when the caller raised `steps` for accuracy. A fix that reproduced
   the failure mode it was written to remove.
3. **`maxRepresentableSteps` named a step count that also fails.** `Math.max(1, ...)` turned a
   limit of 0 into 1, contradicting the helper's own documented contract. Also introduced by the
   round-one fix.
4. **`parametricVar` returned `-0`.** Round one hardened `toLosses` and stopped there. Worse, the
   sweep added in round two to prove the class was closed used only confidence levels at or above
   0.5, where the quantile is non-negative — so a file whose stated claim is that the rule is
   checked _everywhere_ missed it.

Writing the regression tests then surfaced a fifth, the `sigma sqrt(T)` underflow above.

**What this says.** A fix carries the same blind spot as the code it repairs, because it comes
from the same model. Two of the four new defects existed only because of the previous round's
fixes. The rule that follows is in CLAUDE.md: run the verifier _after_ fixing, not only before.

It also says something about coverage. The suite stood at 98.65% statements and 97.4% branches
when the first five defects were found, and every one of them was in a covered line. Coverage
measures execution, not correctness. It earned its keep exactly once, on `maxRepresentableSteps`,
where an uncovered branch was a real defect in new code — worth running, worth not trusting.
